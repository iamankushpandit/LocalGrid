Message marker icons

Four states, four distinct shapes instead of one tick repeated. For owner review before any code is written (D31). Every glyph below is one this build can already draw — each is labelled with the exact LV_SYMBOL_* constant, so nothing here needs a new font.

Why the old markers could never work. In the theme today accent and success are the same value, 0x5FD38D. So "delivered grey, read green" and "delivered green, read green" were asking two identical colours to carry different meanings. The pair of ticks was not hard to read — it was impossible. Distinct shapes fix that; distinct colours alone could not.

The waiting glyph — settled: the clock

Decided and shipped: a clock face, U+1F553 from the emoji font. The turning arrow was rejected for a good reason — LV_SYMBOL_REFRESH already means retry on this handheld, being the Reconnect action's shape, so using it for "not sent yet" asked one glyph to carry two unrelated meanings. A clock says "time passing", which is what this state is.

It costs nothing extra: U+1F553 was already in the committed Noto Emoji subset, so no font was regenerated and no glyph embedded. A true hourglass (U+231B) was the first choice and was dropped once its price was clear — the font generator emits one size only, so an hourglass would have meant a second font target, a second generated .c, and a second LV_FONT_DECLARE. The clock also forced one real design consequence: the emoji font has exactly one size, 20 px, so the marker glyph is drawn at font_icon while the timestamp beside it stays at font_tiny. Asked for inside a 10 px line, it would not have drawn at all.

Waiting is only visible for any length of time when the handheld is off the grid — which is precisely when it matters, because it is the difference between "gone" and "still in my pocket". That argues for a mark rather than nothing: an absent icon cannot tell you which of those you are looking at.

Groups and broadcasts

You asked for delivered and read counts on groups, and for broadcasts to show only as far as the grid carrying them. Both fit what the core already does — with one honest exception, below.

ConversationMarkerReads as
1:1 One icon, the furthest state reached.
Group, partly read 3/4   1 Three of four handhelds have it, one person has opened it.
Group, all read all read Counts collapse once everybody has opened it.
Broadcast  →  4 On the grid, then how many handhelds confirmed it. No read state.

One thing I cannot honestly show. You described a broadcast as "sending it, receiving it in AP, then AP delivering it". The first two are real states. The third is not: no node ever reports back "I have finished handing this out" — there is no such message in the protocol. What is real is that every receiving handheld confirms delivery individually, so a broadcast can show a count of handhelds that have it. That is strictly better information than an AP claim would be, but it is a count rather than a completion, because the grid does not know how many handhelds are switched on.

Colours come from the theme, not from the screen

Your point stands and it needs a theme change, not just discipline. There is no role today meaning delivered or read; borrowing success and accent would bake marker meaning into unrelated roles — and they are the same colour anyway. So four new roles go into lg_theme_t, screens ask for them by name, and a future theme changes all of it in one file.

Proposed roleDefaultCarriesChosen because
mark_wait#7FA78F WaitingThe existing muted green: recedes, because nothing has happened yet.
mark_node#4A8FD4 On the gridA blue, deliberately not green: the grid has it, the person does not.
mark_delivered#5FD38D On their handheldThe theme's green, which already means "good" everywhere else.
mark_read#B98CFF ReadDecided. A violet, so read cannot be mistaken for delivered at 13 px. The only value outside the green palette, and deliberately so: stepping out of the greens is what guarantees the two states can never collapse into each other again.

What I would build once you pick

  • One icon per bubble, not a row of them. The marker shows the furthest state reached, so the bubble stays quiet and one glyph changes in place.
  • Group read needs one line widened in the chat screen, which currently reports reads only for 1:1. Group delivery counts already arrive today — every member's handheld reports, and the core counts per member.
  • No wire change and no reflashing nodes for any of this. It is screens, the theme, and one scope widening.
  • Rejections keep their words. "That handheld is offline" cannot be said by any icon, so refusals stay as text in the error colour.

All settled and built: Set A, violet for read, and a clock for waiting. Recorded as D42 and on both handhelds. It needed no wire change and no reflashing of APs — screens, four new theme roles, and one line widened so group reads are reported as well as 1:1.

Still unproven on hardware: the group counts and the group read reports, and whether the clock glyph draws at all. Serial output reports states and counts, never pixels, so that last one needs somebody to look at a panel.
