ESP32 · ESP-IDF · Prototype

An offline network built from inexpensive ESP32 boards.

LocalGrid turns ordinary ESP32 boards into a self-forming network. Access points find each other and form a mesh by themselves, and touchscreen handhelds send text, emergencies, and push-to-talk voice across it. No Internet, no phones, and no cell service, ever.

How it works

There are two kinds of device. Access points are small boards with no screen that you place around the area and power; they carry the messages. Handhelds are the touchscreen devices people carry.

  1. Place and power the access points. Up to eight, in any order. They share one network name, find each other by radio, and link up on their own. Nothing to set up after the first time.
  2. Handhelds connect to a nearby access point. Each picks one with a good signal, the load spreads across access points, and a handheld switches as you walk. Up to 32 handhelds.
  3. Messages hop between access points. Private, group, and everyone messages hop from access point to access point until they reach the right people, and the sender sees when they arrive.
  4. Set it up from any phone or laptop. Join the network's Wi-Fi and open the admin page to name the network, add people and groups, and set the time. A new access point serves it in setup mode; after that it runs only when an admin turns it on, with web on at the console or over the Bluetooth admin link, and switches itself off when that window closes (15 minutes by default), so the access point's memory goes to handhelds (D91).

Designed to keep working

If an access point fails, only the area it covered loses signal; the rest of the network carries on. When a device restarts, it gets back what it knew from the devices that stayed on.

Every device has fixed limits built in, so a busy network slows down instead of crashing. Every design choice is written down, with the reasoning, in the project's documents.

What is ESP-NOW?

ESP-NOW is a radio protocol built into every ESP32 by Espressif, the chip's maker. It sends short packets straight from one board's Wi-Fi radio to another's. There is no router, no joining a network, and no Internet involved. LocalGrid's access points use it to talk to each other.

  1. Say hello. When an access point starts, it broadcasts a hello on the network's channel: five times, 200 ms apart, then every 2 seconds.
  2. Become neighbours. Every access point that hears the hello adds the sender as a neighbour. No pairing, no setup, and power-on order does not matter.
  3. Pass messages on. A message goes to each neighbour, which passes it on to theirs. Each access point ignores copies it has already seen, and a message stops after 3 hops, so nothing circulates forever.
  4. Work around a lost access point. A neighbour that misses three hellos (6 seconds) is dropped, and messages keep flowing through the access points that are left.

One radio, one channel

Each access point runs ESP-NOW and the Wi-Fi network the handhelds join at the same time, on one radio and one fixed channel. Handhelds use Wi-Fi to reach their access point; access points use ESP-NOW to reach each other.

Slow on purpose, for range

Access points talk at 1 Mbps, the slowest Wi-Fi rate, because slower signals reach farther. That is still plenty: one packet holds up to 1,470 bytes, enough for a whole message or a slice of voice.

Encrypted by LocalGrid

ESP-NOW's built-in encryption cannot protect messages sent to everyone at once, and it uses up connection slots the Wi-Fi side needs. So LocalGrid encrypts every message between access points itself, with a key only that network's devices hold.

What it does today

Everything below runs on the test boards. It is a prototype: expect rough edges, and read the status section before you rely on it.

Private messages stay private

A private message is encrypted on the sender's handheld and only decrypted on the recipient's. Access points carry it without being able to read it. Group and everyone messages are encrypted over the air too.

Emergencies get through

An urgent message appears on every screen, even a locked one, and the sender sees who has read it.

Push-to-talk

Hold a person, a group, or everyone to talk, like a walkie-talkie (D88). Voice is encrypted like text and levels itself so quiet and loud voices come through evenly. The Freenove handheld has a microphone and can talk; the Hosyond has none, so it listens.

Recovers after a restart

What one device knows that others need, such as who is on the network and which groups exist, is copied to its neighbours. A device that restarts gets it back from them, and the newest version always wins.

Its own clock, and GPS

The network keeps its own time. It survives a restart that keeps power, and handhelds bring it back to access points that lost it. A GPS module on MAIN sets the time from satellites and shows where MAIN is, with map links, on its admin page. A handheld can carry its own GPS too, and then it backs up the time as well.

Everyone on a map

A handheld with a GPS shares its position with the network, so the admin page can show where people are and a handheld can show how far it is from the access point with the GPS. A single position is held in memory only; the last steps of a walk, its trail, are kept in flash so they survive every device being off (D106). A handheld without a GPS simply does not appear.

Watch the network without joining it

Every access point broadcasts a sealed Bluetooth status. A laptop or phone nearby can show the health of each access point, who is online, batteries, and any alert, without joining the network. It only listens: no message text, no voice, and it never takes part.

A simple touchscreen interface

Handhelds have their own lightweight interface with a phone-style keypad. It adapts to the screen it runs on, so supporting a new display board is mostly a matter of describing its pins and screen.

LoRa: the second path

LoRa is a low-power, long-range radio that works below the Wi-Fi band. It is built to reach farther than Wi-Fi, but carries far less data; LocalGrid has not measured its range yet. ESP32 chips have no LoRa radio, so it means adding a small LoRa module to a board. The access points use it today: a message is acknowledged over LoRa and sent again until it arrives (D104), and one that Wi-Fi could not deliver goes over LoRa at once (D105).

Access points first

Access points too far apart for ESP-NOW still reach each other, so two groups of access points that Wi-Fi cannot bridge become one network. The LoRa link carries messages, alerts, who is around, positions and the time, but never live talk. A module is optional: an access point without one simply uses Wi-Fi alone.

Handhelds too

A handheld with a module does not go silent when it walks out of Wi-Fi range: it still sends and receives messages and emergencies through an access point over LoRa, shown to others as reachable by LoRa, with live talk returning once it is back in range (D77, D80, D109). It stays optional, since each handheld needs the extra module.

What stays the same

Wi-Fi and ESP-NOW stay the main links, because they are fast enough for live talk. LoRa is the long-distance path for short, important messages. The aim is for encryption, groups, and emergencies to work the same way over either.

The basics

What is LocalGrid, and who is it for?

An offline network you set up yourself. Small ESP32 access points, placed around an area and powered, find each other and form a mesh on their own. People carry touchscreen handhelds and send private, group and everyone messages, emergencies, and push-to-talk voice across it.

It is for groups that need to stay in touch where there is no signal: a group trip several families take together, an event site, an exercise or a drill. Today it is a prototype, best suited to people who build and test hardware.

Does it need the Internet, a phone, or an account?

No. The network never uses the Internet, there is no server, and there is nothing to sign up to. A handheld is a complete device on its own: one handheld is one person, with no logins (D7).

A phone or laptop is needed only to look after the network: join its Wi-Fi and open the admin page to name the network, add people and groups, and set the time. After the first setup the page is opened on request, so the access point's memory goes to handhelds the rest of the time (D91).

Can it connect to the Internet, or to people's phones?

No, by design. There is no gateway to the Internet or to the phone network, and no app for sending messages from a phone.

A laptop running the project's dashboard, or the Android watcher app, can sit beside the network and watch it over Bluetooth without joining: alerts, which access points are up, who is online, and batteries (D68, D69). With the admin password it also sees what the admin page shows, such as the map. It has no way to read a message, hear a talk, or send anything (D70).

How is it different from Meshtastic and other LoRa meshes?

LoRa meshes such as Meshtastic trade bandwidth for range and usually pair each radio with a phone. LocalGrid's main links are Wi-Fi: ESP-NOW between access points, and Wi-Fi from each handheld to its access point. That covers a smaller area and needs powered access points; in return the handhelds stand alone with no phone, carry live push-to-talk, and show who has read an emergency.

LoRa is LocalGrid's second path: between access points when Wi-Fi cannot reach (D74), and to handhelds that carry a LoRa module (D77). Live voice never crosses LoRa; a compact copy of a talk can (D95).

Why not walkie-talkies, or a phone mesh app?

Push-to-talk works like a walkie-talkie: hold a person, a group, or everyone, and talk (D61, D88). LocalGrid adds written messages, one-to-one conversations that are end-to-end encrypted, groups, and emergencies that take over every screen, even a locked one, and tell the sender who has read them (D57, D58).

It needs no phone at all. The handhelds are their own devices, and the network is carried by access points you place, so it does not depend on anyone's phone being charged, nearby, or set up.

Hardware, size, and range

What hardware does it run on, and how many boards do I need?

Common ESP32 boards. An access point is an ESP32 dev board (any 4 MB ESP32). Handhelds are ESP32 touchscreen display boards, listed under Hardware, plus a small alert unit that shows alerts and raises an SOS (D66). A GPS module and a LoRa module are optional.

One access point is enough to start: it serves handhelds on its own. More access points add coverage and room for more people. The project is developed on a bench of three access points and six handhelds.

How many handhelds can one network hold?

Up to 32 handhelds and 8 access points in one network, with up to 8 groups, and a message crosses at most 3 hops between access points. These limits are fixed in the code, so a full table gives a defined, logged result instead of crashing.

Per access point, the firmware keeps 8 handheld sessions (D93), but memory decides how many it can really serve. Measured alone, one access point served all six bench handhelds and still had memory free; the real ceiling has not been measured yet (capacity and memory). Handhelds spread themselves across the access points they can hear (D54).

How far does it reach?

Not measured yet. Every test so far has run on one workbench with every board in radio range, so there is no measured range to quote, for Wi-Fi or for LoRa. The distances in the table at the top of this page are estimates for these boards, not measurements.

A field test will replace them. If you run one on your own boards, we would like the numbers.

How long do the batteries last?

For handhelds, it has not been measured.

For access points, two overnight runs recorded how long each kept running on a 5000 mAh pack: between 9 h 19 min and 12 h 42 min, with the one carrying a GPS the shortest both times. The boards cannot report their own charge, so these are floors read from when each went silent, not a battery-life rating (the run's report).

Is LoRa legal where I am?

Check your local radio rules before you transmit. The modules used are Reyax RYLR998 for the 868/915 MHz bands (D71). The firmware sets 868.5 MHz, and one setting changes it for a 915 MHz region (LoRa notes). Transmit power is 22 dBm by default and can be turned down (D98).

The firmware counts airtime but does not yet enforce a region's duty-cycle limit, so staying within your region's rules on frequency, power and airtime is up to you.

Security and privacy

Is it encrypted?

Yes, by LocalGrid itself rather than by the radio. One-to-one messages and one-to-one talk are end-to-end encrypted (X25519, HKDF-SHA256, ChaCha20-Poly1305): access points carry them and cannot read them (D5, D61). Group and everyone messages are encrypted over the air, but an access point can read them (D5).

Everything between access points, over ESP-NOW or LoRa, is sealed with the network's own key, and the encryption is checked against published RFC test vectors on the boards. Keys sit in each device's storage, which is not encrypted, so someone who takes a device can read them (D96).

Who can see where I am?

Only a handheld with a GPS shares a position; one without a GPS never appears. Positions are shared within the network: other handhelds use them to show where an alert came from and how far away people are, and the admin page and a watcher holding the admin password show them on a map (D65, D70). The Bluetooth status beacon carries no positions (D68).

A single position is held in memory and forgotten on restart. The last sixteen steps of a walk, its trail, are kept in flash on purpose, so a device found after its owner got lost still shows where they went (D99, D106). A handheld can stop sharing its trail from its My trail page. Positions are not logged.

When things go wrong

What happens when an access point fails?

Only the area it covered loses signal; the rest carries on. There is no master and no server: every access point holds a full copy of the settings, groups, who is online, the time, and the health history, each record versioned so the newest wins (D45, D48).

Handhelds in range of another access point move to it, messages route around the gap, and a message Wi-Fi could not deliver between access points goes over LoRa at once (D105). When the access point comes back, it recovers what it knew from the ones that stayed up.

What if everything loses power at once?

Settings, groups, keys and trails are kept in each device's flash and come back on their own (D48, D96, D106). The clock is the exception, because the boards have no clock battery.

The time survives any restart that keeps power (D60). A restarted access point takes it from another access point or from a handheld that kept it (D53), and an access point with a GPS takes it from satellites (D63). Only after every device has truly lost power, with no GPS, does the admin set the time again (D6).

Will a message wait for someone who is offline?

No. There is no store-and-forward: a message to someone the network cannot reach is refused, and the sender is told straight away, rather than being promised it will arrive later (D13).

A handheld out of Wi-Fi range but reachable over LoRa is shown as such and still gets messages, acknowledged and sent again until they arrive (D80, D109).

How was it tested?

Every test runs on real ESP32 boards, never a simulation on a PC (D25). The protocol core and the encryption run their unit tests and RFC test vectors on a board.

The self-healing claim was tested by attacking it: a framework kills access points and handhelds, cuts their power and switches their radios off at random for hours, while the handhelds keep messaging. In the 10-hour run of 2026-09-18, 55 faults were injected and 55 recovered with nobody stepping in, and the backbone re-formed in a median of 3.7 s. It also found bugs that code review and unit tests had missed (how it was chaos tested). It has not yet been tested in the field: every run so far was on one workbench.

Building and running it

Can I build one? How do I install it?

Yes. From source: install ESP-IDF v6.1 and follow the README's Build it steps.

From the browser: the installer page flashes a board over its USB cable from Chrome or Edge, then gives the board its place in your network. A network's keys are made once and handed to each device at setup rather than built into the firmware, so one published image can serve every network (D96). Images are not published on this site yet; until they are, build from source.

How does it get updates?

Only signed ones. A device installs firmware only if it is signed with the release key it was given at setup, and a device given no release key takes no update at all (D97). The signer page makes a release key and signs firmware in your browser.

Give a signed update to one access point and it spreads to the others by itself, one at a time (D101). Access points also carry handheld updates and hand them to handhelds over Wi-Fi, sharing the images for different chips between them (D107, D111). A device installs an update on its own, never during a talk or an alert and never below 30 % battery, and new firmware runs on trial and is kept only if it starts.

The project

Is it a product I can buy?

No. LocalGrid is an open-source prototype. It runs on development boards with modules wired on; purpose-built handhelds are still being designed, and the access points have no cases yet.

Can it carry things other than text and voice?

The network itself carries typed, sealed messages between devices; text and voice are two of those types, alongside names, positions, groups and firmware updates. Adding a new type is a documented change to the protocol core (its envelope, body layout and tests), so sensor readings, drone telemetry, trackers or a gate that reports being opened are all possible. None of them is built, and the code is open for anyone to build them. The same goes for watching: the laptop and Android watchers read the access points' Bluetooth beacon and only listen (D68, D70), and the same pattern could become a sensor or drone watcher.

What does it not do yet?

Measured range and field testing; purpose-built handhelds and cases; handhelds relaying for each other, which is planned (D47); holding messages for someone offline (D13); and LoRa directly between two handhelds, which goes through an access point instead (D77). Read the milestone reports before relying on any part of it.

What licence is it under?

GPL-3.0-or-later (D76). A company shipping devices with it must publish its changes and leave the boards reflashable. Contributions are accepted under the same licence, with no contributor licence agreement. Third-party material keeps its own licence (THIRD_PARTY.md).

Can I contribute, or port my board?

Yes. Start with CONTRIBUTING.md. Porting a display board mostly means describing its pins, screen and touch controller in one profile file; docs/BOARDS.md lists the fields and the bring-up checklist. Range tests on your own radios are just as welcome, and the admin page can be worked on with no hardware.

Build it with us

LocalGrid is written in the open, decisions and all. These are the places a contributor helps most.

Port a board

Describe a board's pins, screen, and touch controller in one file. If you have an ESP32 display board that is not listed, you can probably bring it up.

Test on real radios

Measure range, handover as you walk, and recovery on your hardware and in your space. A test tool switches access points off at random for hours and reports how the network recovers.

Improve the admin page

The web page every access point serves for setup. Try it here against a simulated network, no hardware needed.

Review the messaging and encryption

The code that carries and encrypts messages is plain C, checked against published test values. Careful reviewers are welcome.
